## Executive summary (code-grounded)

This monorepo is not a greenfield airdrop game scaffold. The shipped centre of gravity is an **AI Judge engine** (text scoring + farming flags + account rollups) with **multi-platform ingestion**, **async scoring pipelines**, **credit/Stripe monetisation**, and a substantial **SPORE graph API** layer (~4,248 Python LOC) that composes LLM scores with relationship evidence. Spin-off **A** (reputation / anti-farming) reuses roughly **65–70% of backend logic and 35–40% of frontend UI** with deletions mostly cosmetic or gamification-adjacent. Spin-off **B** (marketing creative judge) reuses only the **scoring transport shell** (~20–25% backend, ~15–20% frontend) because every prompt, dimension, crawler, and graph feature is Web3-contribution-specific today.

**Recommendation tied to code, not theory:** Make **A the primary ship track**. The repo already implements the differentiated wedge described in Episode 1 sources — post-identity **content quality + farming detection + account rollups** — while B would require rewriting rubrics, deleting half the backend, and still lacking any ad-platform integration surface. Run B only as a **thin rubric-pack experiment** (new `ScoringRubric.custom_instructions` + landing reword) on a subdomain; do not fork the monorepo for it unless PLG converts in 30 days.

## What exists today (inventory)

### Backend — `judge` + `ai_core` (the engine)

Two layers, one product behaviour:

| Layer | Role | Shippable artefacts |
|-------|------|---------------------|
| `apps/judge` (~916 LOC) | Compatibility + HTTP | `JudgeDemoView` (anon throttled demo), `JudgeScoreView` (auth + credits), `JudgeScoreAccountView` (NDJSON Twitter account stream, 5 credits), `ScoringRubric` CRUD, `JudgeCache` content-hash dedup |
| `apps/ai_core` (~1,397 LOC) | Canonical scorer | `AICoreScoringService.score_text`, heuristic fallback on budget/API failure, `run_scoring_pipeline` Celery workflow, Prometheus metrics, Twitter SNS analysis endpoint |

The scoring contract is stable and repeated everywhere: **teaching_value, originality, community_impact → composite_score + farming_flag (genuine/farming/ambiguous) + explanations**. `judge/service.py` delegates to `ai_core` and persists cache rows keyed by SHA-256 of normalised text — identical content never pays twice for LLM.

`JudgeScoreAccountView` (`judge/views.py` L188–322) is the A-side killer feature already coded: fetches up to 25 tweets via Twitter v2, batch-scores with Claude, streams per-tweet scores, emits aggregate `farmingPercentage`, `genuinePercentage`, strengths/weaknesses, verdict. This is not stub code; it has error handling for 429, JSON fence stripping, and credit gating (Pro/Team only).

### Backend — `contributions` (ingestion → score)

~1,528 LOC. Production-grade incremental crawlers for **Twitter, Reddit, Discord, Telegram** (`crawlers.py`), with cursor state on `CrawlSourceConfig`, Celery tasks (`crawl_source_config_task`, `crawl_all_active_sources_task`), dedup via `(platform, platform_content_id)`, and automatic enqueue of `score_contribution_task` on new rows. Twitter/Reddit items also feed **SPORE graph ingestion** (`record_twitter_item`, `record_reddit_item`).

The `Contribution` model stores the full judge output plus `xp_awarded` — gamification coupling that A can ignore at API level but B should delete conceptually.

### Backend — `spore` (unexpected moat, A-only)

~4,248 LOC — largest app in the repo. Multi-tenant API with API keys, quotas, audit logs, graph nodes/edges, relationship analysis runs, and `compose_contribution_score` which blends **80% LLM composite + 20% graph component** from `contribution_graph_features`. Stripe plans (`starter` $99, `growth` $499, `enterprise`) wired through `payments/services.py` with tenant quota fields.

Neo4j is **optional** (`SPORE_NEO4J_ENABLED=false` by default in Docker); Postgres graph models work without it. This is enterprise-shaped infrastructure already present — far beyond anything B needs.

### Backend — monetisation & auth

- **Payments** (~1,193 LOC): dual tracks — SPORE tenant subscriptions AND per-user AI Judge credits (`free` 10 / `pro` 200 / `team` 1000 monthly). Credit packs, Stripe checkout, `deduct_credit` on score endpoints.
- **Accounts** (~584 LOC): SIWE wallet verify → SimpleJWT. **Not Dynamic.xyz** as `CLAUDE.md` claims — code uses standard SIWE signature verification.

## Moat already coded (not slides — running code)

1. **Farming tri-state with explanations** — persisted on `Contribution`, cached on `JudgeCache`, surfaced in `ScoreCard` with screen-shake UX for `farming`. This is the post-Passport differentiation web research identified.

2. **Content-hash idempotent scoring** — `JudgeCache` + `AICoreScoringService.hash_content` prevents replay cost explosion; critical for API pricing.

3. **Account-level rollup** — batch tweet scoring + `farmingPercentage` / `genuinePercentage` / verdict in one NDJSON stream. Competitors sell wallet graphs; this sells **what the account actually posts**.

4. **Multi-platform crawl → async score loop** — four crawlers, cursor incrementalism, tests in `test_crawlers.py`, `test_tasks.py`. Ready for protocol "watch these sources" pilots.

5. **Graph-augmented score (SPORE)** — `compose_contribution_score` fuses text + relationship strength. No MarTech competitor in the B lane has this; it's A's enterprise upsell.

6. **Configurable campaign rubrics** — `ScoringRubric` with weighted dimensions + `custom_instructions`. Admin CRUD exists. Protocols can tune scoring without redeploying prompts (partially — base prompt still Web3).

7. **Monetisation hooks** — credits, plans, Stripe models, tenant billing. Rare in demo-stage repos; means A can charge for account analysis now.

8. **Heuristic fallback** — when Anthropic budget/rate fails, `score_text_heuristically` still returns structured scores. Operational resilience for demos under load.

9. **Streaming UX** — NDJSON partials in Next route + client parser in `useAiJudge.ts`; polished conversion demo already wired to waitlist CTA.

## Risks (specific, from this repo)

### Husky / lint-staged

`package.json` declares husky + lint-staged but **no active pre-commit hook** was found under `.husky/`. The `prepare` script silently passes. Solo velocity is fine; team scale or CI parity will drift — eslint/prettier won't gate commits locally.

### Vercel / serverless judge path

`app/api/judge/route.ts` uses an **in-memory `Map` rate limiter** (10 req/min/IP) with an explicit comment that it resets on cold start and is per-instance. On Vercel serverless this is porous at scale. Marketing demo also **bypasses Django `JudgeCache`** and credit system — authenticated `(app)/judge` page still calls `/api/judge` via `useAiJudge`, so the credits UI is partly theatre for text scoring (account tab correctly hits backend with credits).

**Triple prompt duplication:** identical Web3 rubric lives in (1) Next `/api/judge`, (2) `ai_core/service.py`, (3) `judge/views.py` account batch prompt. Any rubric change for A/B requires three edits — guaranteed drift.

### Particle vs wagmi vs CLAUDE.md Dynamic

Runtime stack: **Particle ConnectKit (alpha)** for connect UI, **wagmi** for chain config, **SIWE** backend — no Dynamic SDK. `CLAUDE.md` still documents Dynamic.xyz → JWT. Risk: wrong provider docs, double wallet abstraction (Particle wraps wagmi connectors), alpha dependency (`3.0.0-alpha.3`) in production `package.json`. For A MVP, wallet auth is optional until on-chain rewards; for B, wallet is dead weight.

### Operational surface area

Docker compose runs postgres, redis, neo4j, celery worker, celery beat, backend, frontend. SPORE + crawlers + dual billing is **solo-maintainer heavy**. Shipping A in 90 days requires **scope denial**: Neo4j off, contracts parked, gamification pages hidden.

## Recommendation (code-tied)

**Primary: Spin-off A on this monorepo without fork.**

Evidence:

- Largest engineered surfaces (`spore`, `contributions`, account NDJSON analysis) all point at A.
- Farming flag + account rollup + crawl pipeline is a coherent API product today.
- Monetisation (credits, Stripe) aligns with A's "score accounts before you allocate" pitch.
- B reuses the smallest, most commoditised slice (LLM JSON scoring UI) while requiring the largest deletions (graph, crawlers, farming semantics).

**Secondary: B as 30-day experiment only** — implement as alternate `ScoringRubric` rows + marketing landing section on subdomain; do not delete spore/contributions until B proves conversion. Maximum reuse: `ScoreCard` shell + `createScoreStream` pattern + payments.

**Immediate engineering fixes before either ship:**

1. Unify scoring prompts into `ai_core` single source; Next route proxies Django or imports shared prompt constant.
2. Wire authenticated judge page to credit-gated backend endpoint.
3. Replace in-memory Vercel rate limit with Redis/Upstash (`redis` already in frontend dependencies).
4. Update `CLAUDE.md` auth stack (Particle/SIWE) and product priority (judge API > gamification).
5. Add `.husky/pre-commit` or remove husky to avoid false confidence.

**Contracts, skill trees, loot:** not shippable moat in 90 days — park them. The moat that is already coded is the judge + ingestion + optional graph — and that is spin-off A.
